# 《工作方法演示》逐页讲稿

本文件用于现场逐页讲解，与定版 Deck 和 runbook D1–D8 对齐。本轮正常、缺陷、恢复后的双引擎云端运行和 Agent 反馈已实录；另在练习目录实录了安装和需求到测试的生成过程。主线实测使用仓库审阅版。现场控场以 runbook 为准；自助视频采用 [独立口播与画面安排](video-script.md)，包含必要前置，剪短下载、生成和执行等待。Deck 保留已审阅的页面，视频说明页的示例截图与实操均对齐本轮证据。

## 02 · 点了再玩一次，新一轮真的开始了吗

时间：0:45–3:00

用户答完一组题拿到十分。点击再玩一次后，进度要回到第一题，得分必须清零；再次完成挑战，还应能返回主页。我们围绕这个要求生成并审阅用例，实际运行后观察判定，再故意让应用保留旧得分，看同样的测试能否发现问题。恢复后的云端提交保留这条主线，同时加入应用已有的英文场景，用另一种引擎执行。

**操作提示（不口播）**

打开应用与产品需求 F4，指出十分、重玩按钮和清零要求。不手工答完十道题。说明主线共三次运行，第三次云端提交含两个任务。截图是归档实测。

## 03 · 业务需求如何成为测试用例

## 04 · 重玩之前先真实到达结算页

时间：4:30–6:00

第一个场景先打开首页、进入第一组，再由确定性代码按需求题库答对十道题，真实到达 10 分的结算页。三个场景配置相同的 scope，gherkai 将它们编成一个执行任务，按书写顺序共用浏览器会话。因此第二个场景接着使用这张结算页，第三个场景也能继续后面的流程。向下展开的是第二个场景。本例的 Given 由匹配到的确定性步骤自动检查已有得分，记录重玩测试的前置状态是否符合要求。之后继续点击与清零检查。QA 审阅业务期望和用例设计，运行时的条件检查由工具执行。

**操作提示（不口播）**

先指明三个 scenario 上相同的 scope，再沿下箭头展开第二个场景。本例 Given 匹配确定性检查，并非 Given 关键字本身自动提供校验或状态准备。前置校验不是自动门禁：普通断言 failed 仍继续后续步骤，执行 error 才触发跳过本场景后续步骤。强调跨 scenario、同一 scope 的浏览器会话复用。不会自动补回被筛掉的前置场景，也不是从过去一次 run 保存的状态继续。不给接续链添加会重新导航首页的 Background。

## 05 · 运行前确认测试范围与执行方式

时间：6:00–7:30；约 7:00 发起本机运行

现在用 gherkai plan 核对执行计划。表里依次检查：是否选中了完整的三个场景，它们是否在一个浏览器会话里按顺序运行，引擎是不是 Midscene，以及总共有多少步、每步由什么执行。十四个确定性步骤、七个 AI 步骤和一次导航，合计是三个场景的二十二步。计划确认后才启动第一次本机测试，随后查看实际得分检查代码。

**操作提示（不口播）**

将终端 plan 输出逐项对应表格的四行，再指向逐步的执行方式标注。只对主线统计 22 步；后面含英文场景的组合计划为 33 步。约 7:00 发起正常 run，保持执行终端，切第 6 页。

## 06 · 得分为 0 怎样执行与判定

时间：7:30–10:30；本机运行期间

用例写的是得分为零。注册模式匹配这句话，把期望值交给 scoreIs；它先确认答题页可见，再等待页面得分文字等于期望值。如果超时仍不一致，代码会形成失败消息，包含期望值、实际值、页面地址和元素位置。这既给出失败判定，也为人或 agent 提供排查依据。gherkai skill 指导编程 agent 将这些诊断信息写进确定性步骤代码。确定性检查本身不产生 AI 思考轨迹或截图，页面现场需结合这次运行中相应的证据读取。接着到运行记录中看 AI 点击和得分判定。

**操作提示（不口播）**

打开 quiz.mts 的注册，以及 _checks.mts 的 scoreIs、expectText，展开失败分支中的消息拼接。指出它返回期望、实际、页面地址与选择器，不只返回失败二字。这里显示的是主线实测使用的仓库代码；前面的生成片段已说明基础能力复用，不把这项已有检查说成新生成的。

**画面切换**

## 07 · 不只看到页面变化，还能核对验收结果

时间：10:30–12:00

现在把正常运行的结果和原用例对上：点击操作完成，进度回到一比十，得分是零，后续也能返回主页。我们可以沿着用例逐项复核，而不是只看一个总的通过标记。AI 操作的执行轨迹和精确检查的判定说明了结果从何而来。接下来保持用例和验收要求不变，只让应用出现一次得分未清零的问题，看看同样的测试能否发现它。

**操作提示（不口播）**

按 D4 从 normal.json 取 DEMO_NORMAL_RUN，读取 explain，再展开重玩场景 step 1 的 AI 证据。未终态时明确切换归档结果，不宣称本次已通过。下一次注入须等本次正常运行结束，不能在它执行期间修改被测应用。

**画面切换**

## 08 · 按钮点到了，得分却没有清零

时间：12:00–17:00；先注入并启动缺陷运行

演示者故意保留上一轮分数，再执行同一用例。gherkai explain 给出人可读的业务步骤、判定和失败原因。保存的实测中，点击已完成，进度回到第一题，但分数仍为十分。确定性检查返回了期望与实际不符的说明，还可以结合本次运行的页面现场核对。通过 explain 的 JSON 输出，agent 可以读取失败说明、步骤定位，以及可用的证据入口。它不是只把说明文字放进 JSON，而是提供后续处理所需的结构化反馈。

**操作提示（不口播）**

先看 explain 的人读说明，再看同一 run 的 JSON。得分确定性步骤的失败消息与相关 AI 步骤的页面证据分别查看，不能声称每个确定性步骤都自动截图。保持同次运行，不混用归档或当前结果。随后进入 Agent 反馈循环。

**画面切换**

PPT 提出缺陷验证目标 → 注入改动与第二次 run → 本次失败原因及页面现场 → 回 PPT 对照 0 与 10 → Agent 反馈页。

## 09 · Agent 根据反馈决定下一轮验证

时间：17:00–20:00；E7 约 2 分钟，随后恢复应用

把原要求、失败运行和读取反馈的能力交给 agent，让它自己核对哪个动作完成了、哪个业务状态没有达到期望、证据是什么。它可以据此建议检查测试实现、补充确定性步骤，也能把依据交给编程 agent 辅助排查应用缺陷。这里复验要带上前置场景，不能只重跑中间的再玩一次。我们看实际工作片段，再恢复演示应用。恢复由演示者完成；修复是否有效，仍要用原验收要求验证。

**操作提示（不口播）**

按 D6 播放 E7，明确它来自录制中标注的失败 run，不能冒充刚才现场 run 的即时输出。E7 使用本轮失败 run 20261010T015058Z-32ff1b 的真实记录，不补写 agent 结论。完整视频制作时，前一段失败与此片段须使用同一录制 run 的证据。确认缺陷测试已终态，片段后按备份 restore，核对差异；不宣称自主修复。

## 10 · 恢复应用后提交云端测试

时间：20:00–22:00；约 21:00 前完成云端提交

应用恢复后，将主线和英文场景提交到准备好的云端后端。先看左边：个人在本机调整应用或确定性步骤代码，运行 gherkai，读取结果与失败依据，再继续调试。本机直接加载步骤代码，适合这一轮快速迭代。右边是团队分工：测试开发和基础设施团队统一发布、维护代码、引擎与运行环境。QA、agent 或流水线提交测试任务，按 run ID 查询状态、结果和证据。共享后端负责推进执行与归集结果，团队可以持续复用已经发布的执行能力。本例两种模式都仍使用 AWS 浏览器与模型。

## 11 · 一次提交中的两种执行引擎

时间：22:00–25:00；云端运行期间

这次提交里有两个任务。中文主线仍由 Midscene 复验，保持正常、缺陷、恢复之间的对照。另一个是现有的英文结算场景，由 Nova Act 执行。它从首页独立开始，答完十道题，检查英文结算内容；它不复用前一个任务的浏览器状态，也没有覆盖重玩清零。两个引擎的确定性步骤分别使用 TypeScript 和 Python，项目已提供成对实现。我们可以按需要选择执行引擎，而提交、查询、读取反馈的工作流程仍由 gherkai 统一组织。

**操作提示（不口播）**
