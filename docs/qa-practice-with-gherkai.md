# 用 gherkai 做 UI 测试：QA 团队的工作方法

本文档说明 QA 团队在使用 AI agent 的前提下如何使用 gherkai：角色分工、需求如何转化为可运行的用例、如何向 agent 分派任务并验收其产出，以及失败时如何修正。本文档不介绍基本概念，包括 gherkai 的定义、每一步的三种执行路径、AI 判定与确定性代码判定、本机与云端后端；这些内容参见 [gherkai 的 README](https://github.com/zhiyanliu/gherkai) 与[用户指南](https://github.com/zhiyanliu/gherkai/blob/HEAD/docs/user-guide/README.md)，这些概念在本项目中的对应实例参见[概念对照](./concepts-in-this-project.md)。命令与选项以用户指南为准。

完整流程依次为：**需求、测试设计（QA 负责，产出简报）、实现（agent 负责，产出 feature 与 steps）、验收（QA 审阅用例与预检结果，测试开发 review 代码）、运行（QA 发起）、修正（agent 依据证据处置并汇报）、沉淀。** QA 不手写 feature，也不阅读代码；agent 不决定测试范围，也不自行运行。

## 1. 分工

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| QA / 测试工程师 | 阅读需求、完成测试设计（划分功能域、列出场景、确定必须精确的检查）、编写测试任务简报、验收用例文本与预检结果、发起运行、阅读结果、决定处置 | 不编写 feature 文本，不编写代码 |
| 测试开发 | review 与维护 `steps/` 中的确定性 step 代码与单测、将 steps 纳入云端 worker 镜像 | 不替 QA 决定测试范围 |
| 部署方 | 部署与维护团队共享的云端后端 | 不参与写用例 |
| AI agent（已安装 gherkai skill 的 Claude Code、Codex 等） | 按简报编写 feature 与确定性 step、自查注册与预检结果、阅读失败证据、给出修正建议并汇报 | 不自行决定实际运行、不修改需求口径 |

agent 替 QA 完成的是实现工作：将测试设计转写为 Gherkin 与代码，并用工具核对。测试范围与精确程度仍由 QA 判断。

## 2. 一次性立项

以下步骤在项目开始时执行一次，之后的简报无需重复说明：

1. 安装命令行工具与本机 worker：`uv tool install 'gherkai[local]'`；使用 Midscene 引擎时另需安装 `npm i -g @gherkai/worker-midscene`。
2. 将 gherkai 的 agent skill 安装到项目中：`gherkai skill install --agent all`。安装过程会询问是否将一行提示写入项目的 `CLAUDE.md` 与 `AGENTS.md`，选择是。skill 与命令行工具版本一致，由每位成员在本机安装，不提交到仓库。
3. 编写项目约定，并放在 agent 必定会读取的位置。本项目的项目约定是 [ui-testing-conventions.md](./ui-testing-conventions.md)，`CLAUDE.md` 与 `AGENTS.md` 均指向该文件。项目约定的内容包括：目录与命名、tag 约定、被测地址、界面语言、所有简报默认适用的约束与交付物、agent 不自行运行（只做预检）。
4. 确认被测应用有一个运行时可访问的地址。在本机运行的应用可通过 `--expose-local` 建立隧道，无需预先部署。

## 3. 测试设计：QA 的准备工作

向 agent 分派任务之前，QA 完成以下三项工作，产物是一份简报，而不是 feature 文件。

**以需求文档为唯一事实源。** 用例的每条期望都能在需求文档中找到出处。需求含糊之处先向产品确认，不交由 agent 推测。本项目的需求是 [product-requirements.md](./product-requirements.md)。

**按功能域切分，列出场景。** 切分结果与场景清单写在简报中，feature 文件由 agent 根据简报生成。每个功能域对应一份简报与一份 feature 文件；切分依据是需求文档的功能条目，与组织 Playwright 用例或手工用例的方式相同。每条需求的验收要点在简报中展开为场景，每个场景占一行，写明前置条件、动作与期望。gherkai 对切分方式没有要求，只规定三点：用例写在 `.feature` 文件中；一条 scenario 是一个独立的判定单元；需要沿用上一条 scenario 页面状态的 scenario，用 `@scope` 编入同一个浏览器会话。

**确定必须精确的检查。** 每个场景的期望分为两类，判据如下：

| 走确定性 step（代码判定） | 交给 AI 判定 |
|---|---|
| 数值、计数、精确文本、页面标题、地址 | 页面整体形态、视觉状态（高亮、颜色）、语义判断（「看起来像出错页」） |
| 必须可复现、结果不能抖动 | 一次性检查、页面结构常变 |
| 出现频次高（每条 scenario 都重复出现，或参数化表格的每一行都执行） | 用自然语言更易表达的动作 |
| 答案不在页面上，需要查询数据（如题库） | |

成本与速度也是判据的一部分：AI 步骤每次判定调用一次模型，每步耗时几秒到几十秒；确定性 step 不产生模型费用，在毫秒级完成。连续答十题这类重复动作交给 AI 执行既慢且贵，应写成确定性 step。

界面语言也是需要写入简报的事实。引擎选择由工具负责：agent 根据界面语言为 scenario 标注引擎，并说明理由。

**期望来自需求，定位来自应用，两者不能混用。** 用例中「应该是什么」只能来自需求文档；agent 查看被测应用、阅读其源码，仅用于定位元素、实现动作。如果将应用的现状照搬为期望，测试只能证明应用与其自身一致。本项目曾出现过这种情况：需求只写了「81 个生字对应标准拼音」，没有给出对照表；agent 从应用源码中提取题库作为答案，并配套编写了一条「副本与应用一致」的单测。在这种写法下，即使应用将某个字的拼音写错，测试仍会通过。修正方式是在需求附录中给出题库规格，副本依据规格生成，单测改为检查应用与规格一致。需求缺少规格时应补充需求，而不是从应用中补全。

## 4. 分派任务：测试任务简报

分派任务使用简报，而不是一句简短的指令。简报将 QA 平时向同事交代任务时的要点整理为固定的小标题：功能域与对应需求、被测地址与界面语言、要覆盖的场景、必须精确的检查、交给 AI 判定的检查、补充约束。模板见 [test-brief-template.md](./test-brief-template.md)，可直接复制；本项目各功能域的简报位于 [briefs/](./briefs/)。每份简报对应一个功能域，产出一份 feature 文件。

提供给 agent 的信息分为三层，各层内容放在各自的位置，互不重复：

| 层 | 位置 | 回答的问题 | 示例 |
|---|---|---|---|
| 工具层 | gherkai 的 agent skill | 如何正确使用 gherkai | 先预检再运行、如何编写稳定的确定性 step、失败时先执行 `explain` |
| 项目层 | `ui-testing-conventions.md`，经 `CLAUDE.md` 与 `AGENTS.md` 进入上下文 | 本团队的做法 | 目录与命名、tag 约定、被测地址、每份简报默认适用的约束与交付物 |
| 任务层 | 一份简报 | 本次测试的范围 | 功能域、场景、必须精确的检查 |

判据：对任何一份简报都成立的内容不属于简报，应放入项目层；工具本身的用法不写入项目约定，由 skill 提供。

## 5. 实现：agent 的工作

将简报全文作为一次对话的输入交给 agent。agent 阅读项目约定与需求、查看被测应用、编写 feature，并为两个引擎编写确定性 step 与单测，然后进行自查：对两个引擎分别执行 `gherkai list-deterministic --engine <引擎>` 确认注册情况，执行 `gherkai plan` 检查每一步的标注与 job 数，最后按项目约定的交付物汇报。agent 不实际运行用例。

本项目的两次记录可供参考：选关页简报包含四个场景、四条确定性 step，从阅读材料到交付约 15 分钟；答题页简报包含五个场景、八条确定性 step，并涉及题库提取与切题时长探针，约 40 分钟。耗时主要用于理解与实现，而不是下载。

## 6. 验收

QA 验收以下三项内容，均无需阅读代码：

- **feature 文本**：是否像一条可交给产品确认的验收用例；导航步骤使用需求中的地址；AI 断言是页面级陈述，而不是子串规则；简报中列出的精确检查都由确定性 step 实现；文件头注释说明了引擎选择与分工理由。
- **预检结果**：在 `gherkai plan` 的输出中，每个 step 都标注了由确定性代码还是 AI 执行，且没有冲突标记；job 数即本次运行要启动的浏览器会话数，也决定了费用规模。
- **注册清单**：两个引擎各有一份 `gherkai list-deterministic` 输出，新编写的 step 均已列出。

确定性 step 的代码由测试开发 review，检查项包括：判定带有等待与超时、失败消息包含现场信息、判定逻辑与注册分离、有本地单测、两个引擎的实现成对。agent 在汇报中提出的改进建议（例如某条判定未先确认所在页面已显示）由测试开发决定是否采纳。

## 7. 运行与修正

运行由 QA 发起。在本机运行时使用 `gherkai run`；使用团队共享的云端后端时，执行 `gherkai submit` 与 `gherkai status --wait`。被测应用仅在本机可访问时，添加 `--expose-local <地址>`，运行期间本机需保持开机并联网。

用例未通过时，首先执行 `gherkai explain <run_id>`：该命令将判定结果、原因、模型观察到的内容与截图位置汇总为一份可供他人复现的证据。随后从以下四种处置中选择一种：

1. 断言写法存在歧义：修改 feature 中对应步骤的措辞。
2. 精确检查的 AI 判定结果不稳定：改为确定性 step。
3. 非英文界面上的文本断言判定为失败：更换引擎路由。
4. 以三票重新运行后仍一致判定为失败：认定为被测应用的问题，提交 bug。

每一种处置都必须写入汇报。修改断言与更换引擎都会改变验收口径，如不加说明，相当于在未告知的情况下放宽了用例。由 agent 执行修正时，agent 按相同顺序处置并汇报。

本项目通过隧道在云端实际运行了四份 feature，其中三次修正对应上述处置，这些问题均无法通过本机单测与预检发现：

- **AI 无法可靠判定瞬态状态。** 答对后的绿色高亮仅显示 1.5 秒，随后自动切换到下一题；AI 判定「被选中的选项呈绿色」时，页面已经切换到下一题。处置 2：改为确定性 step「处于答对状态的选项有 N 个」，在点击后同步读取。
- **瞬态窗口内的多个动作必须在一次页面内调用中完成。** 「一题只答一次」最初由两条 step 组成（答对、再点击一个选项），本机单测通过，但在云端判定为失败，失败消息为「再点之后题号从 1 变成了 2：第二次点击落到了下一题」。云端浏览器与 step 代码之间每次调用的往返时间为几百毫秒，三次往返共耗时 8.9 秒。修正方式是将两次点击与读数写成一段页面内脚本，在一次调用中完成，该步骤耗时降至 2.1 秒。由于失败消息包含题号与现场信息，才能直接判断问题出在时序而不是逻辑。
- **隧道访问发现了一个应用缺陷。** 在英文界面场景中，点击语言切换按钮后没有响应，证据指向应用本身：经隧道访问时，页面地址中包含基本认证凭据；应用使用绝对地址写回地址栏，浏览器出于安全原因拒绝该操作，导致语言切换整体中止。处置 4：提交 bug，应用改为使用相对地址。在本机直接打开应用时，该缺陷不会复现。

## 8. 沉淀

- 确定性 step 按主题分文件存放在 `steps/` 中，判定逻辑放在以 `_` 为前缀的辅助模块中并配有单测，两个引擎的实现成对维护。
- 使用云端后端的团队修改 `steps/` 后，需要重新构建并推送 worker 镜像，因为云端使用的是镜像中的版本。
- CI 以 `gherkai run` 的退出码，或 `submit` 之后 `status --wait` 的退出码作为结果。

## 9. 两种 agent 的差别

两种 agent 在本项目中都执行过同一份选关页简报，产出结构相同：4 条 scenario、相同的 4 条确定性 step 模式、两个引擎成对实现、两个引擎各有一份单测，预检结果均为 4 个 job 且无冲突。差别在于操作方式，而不在于结果。

| | Claude Code | Codex |
|---|---|---|
| skill 安装位置 | `.claude/skills/gherkai/` | `.agents/skills/gherkai/` |
| 项目约定入口 | `CLAUDE.md` | `AGENTS.md` |
| 非交互调用 | `claude -p "<简报>"`，通过 `--allowedTools` 限定工具 | `codex exec "<简报>"`，通过 `--sandbox` 或审批选项授予权限 |
| 用时（同一份简报） | 约 15 分钟 | 约 11 分钟 |
| 读取材料的方式 | 逐个读取文件 | 一次并行批量读取多个文件，命令也批量并行执行 |
| 外部信息 | 不联网 | 查阅了三次 Playwright 官方 API 文档，需要允许联网 |
| 汇报形态 | 完整汇报写在对话中 | 对话中给出摘要，交付报告与预检原文写成文件放在 `reports/` 下并给出链接 |
| 「不自行运行」约定的遵守情况 | 约定写成「默认只预检」时，曾有一次自行实际运行；改为禁令加命令清单后遵守 | 遵守 |

注意事项有两点。第一，约定应写成禁令加清单，而不是使用「默认」的表述；这一经验来自 Claude Code，对两种 agent 均适用。第二，Codex 将交付报告写入 `reports/`，该目录是本项目中被忽略的运行产物目录，报告会在下一次清理时删除；如需留档，应让 agent 将报告写入 `docs/` 或对话中。
